## 1. 本次修订的真正目标

实现一套统一、精致、可辨识的**完整游戏美术语言**，让 Home 与各个 2.5D 知识场景属于同一个世界；用户在第一眼能识别角色、路径、分区和词汇节点，并能自然看到侧边学习卡。视觉设计包含页面构图、颜色、材质、地面/道路、节点/展示牌、人物、字体、HUD、光影、微动画和场景切换，而不仅是移动几个区域的位置。

**三项硬性约束：**

1. **保留现有架构。** 不为完成换肤而更换游戏引擎、路由、数据模型、文件目录、地图几何方案或组件层级；需要修改时提出独立理由和最小改动方案。
2. **既有功能不退化。** 地图移动、触发、按键、弹窗、进度、存档等按 V7 保持原样。用户已完成的功能不得无理由重写。
3. **先有对比再合并。** 每次提交附改造前/后同一视角截图，审查可读性与回归测试，通过后才能合并。

## 2. 总体美术方向（默认直接执行）

### 2.1 视觉主题：「纸雕知识庭院 · Memory Atelier」

风格为温暖、清透、略带童话感的**等距视角纸雕微缩世界**：浅色纸张/微缩模型质感、清晰细线边缘、柔和接触阴影、自然的木石与植物装饰，少量金色互动光点。轻立体、易读、有探索氛围；保持思维导图知识结构为画面主角。

- 不做赛博霓虹、深色科幻、高饱和渐变铺满全屏；不做密集按钮墙、强光遮字或过多粒子。
- 全项目只用一套稳定的视觉语言。Area 可以有各自的辅助色，但结构、字体、牌面与标识方式统一。
- Home 继续使用既有 Home 地图图像/视觉，不重新绘制或改变进入机制；可增加非常轻的统一 UI 边框、地点热区光晕和角色脚下投影，使 Home 和 Scene 在观感上衔接。

### 2.3 视觉密度、材质与光照

- **背景**：留白明显、极低对比的纸纹/颗粒；不要用高频花纹抢走单词注意力。
- **场景底板**：柔和暖白/灰绿，纸雕叠层边缘、低高度台基；阴影沿地面投射，不使用大面积黑色阴影。
- **道路/连接线**：维持当前地图通路与几何，外观改为有厚度感的浅石径/嵌铜线；主支关系由线宽（主干较粗、分支较细）和颜色明度体现。
- **环境物件**：每个 Area 只加入少量与语义相关的小装饰。装饰不得覆盖词汇牌、触发锚点或行走路径。
- **光照**：柔和环境光 + 单方向暖光 + 微弱接触阴影；词汇点亮动画可以提亮边缘，不以大面积光柱遮挡画面。
- **性能**：统一复用材质、字体图集和简单几何；特效数量以保持输入顺畅为上限。

## 3. 地图画面的完整视觉设计（不变更当前地图结构）

### 3.1 Scene / Area / Word 三级视觉层级

| 层级 | 主体形态 | 视觉权重 | 始终可辨识的信息 |
|---|---|---|---|
| Scene | 场景中心地标 / 小广场 / 主标题构件 | 最大 | 场景名称、返回 Home 的提示 |
| Area | 色调统一的分组底板 + 清晰区域铭牌 | 中 | Area 名称与范围 |
| Word | 小型展台/图片锚点 + 地面交互光环 | 最小 | 图片、状态；学习模式显示词名 |

保持现有 Area 分布和道路连接。当前是圆形，就将其美术化为“柔和圆角纸雕庭院”；当前是街区，则美术化为“微缩知识街区”。**不得因为偏好某个外形而整体重排地图**。

### 3.2 Scene 地标设计

- 场景出生点配置一个可辨认的小地标：浅石台座、简洁浮雕牌、少量绿植或家具剪影，与 Kitchen/Garden 等语义相符。
- Scene 标题建议使用深色短横幅/悬挂牌，不要覆盖人物头顶；返回节点使用一致的门/箭头符号，并通过附近文字提示 Space。
- Scene 入口的环境色与 Area 色有区分；不要用大型浮空文字墙代替空间层级。

### 3.3 Area 外观设计

- Area 通过**底板轮廓 + 一处标题牌 + 一点语义装饰**构成；不要在同一区域反复显示名称。
- 使用很浅的区域专属辅助色作为内圈铺色，边界使用 1–2px 等效描边，并用短角标/旗帜表达所属类别。
- 单词多时，只增加内部留白、错位展示或镜头视觉密度控制；不擅自删除词汇、挪到其他 Area，也不重新定义通路。
- 地面轻量连接纹路应指向词汇节点；不能堆叠过多连线形成织网。

### 3.4 Word 节点设计

- 视觉主体为**图片 + 小底座 + 状态环**。图片正对镜头或采用稳定易读角度；图像展示区域与人物脚下交互锚点保持直观关联。
- 日常状态以静态低对比边框为主；玩家接近时状态环增亮、底座略抬升 4–8px 等效距离；离开后轻缓回落。
- 学习模式可显示英文名；练习模式严格隐藏目标单词英文名，不通过地面标签、迷你地图、悬停标题或无障碍文本泄露答案。
- 同一摄像机视野里词牌过密时，使用**视觉降级**：远处优先显示简洁图片/图标，靠近时展开标签；不得移除节点、重排知识层级或令已隐藏答案暴露。
- 对每个节点使用投影矩形检验可读性：词牌与 Area 名牌、人物和地图导航提示都应可辨，不能大面积互相遮挡。

### 3.5 主角与动画风格

- 默认角色：圆润比例的“知识探险学徒”，温和色服装，奶油白衣领 + 青绿背带/披肩 + 暖黄小背包；轮廓与地面有明确分离。
- 站立有轻微呼吸；行走采用小步态与足底投影；停在节点附近时不自动遮住节点中心图片。
- 允许玩家已选皮肤继续有效，不更改保存的皮肤标识。

### 3.6 地图视野与文字清晰度

- 视觉中心为角色当前位置及周围一到两个 Area；保留边缘可见的通行方向提示。
- 地图可视区域与外围信息面板之间保持清晰边界，不以浮动的大型卡片压在人物和道路上。
- 文字层次：Scene 名称 > Area 名称 > Word 标签 > 辅助提示；层级靠字号、权重、背景留白表现，不依赖一堆高饱和色。
- 远处词汇可简化标签；靠近词汇时优先保证目标图片、光环和侧边卡片同时清晰。

## 4. 网页整体外观（保留现有布局容器和挂载）

### 4.1 页面框架

保留当前已经实现的顶栏、地图视口、侧边信息区及底部提示区（若存在）。可改变边距、色块、圆角、阴影与响应式尺寸，但**不重新设计 DOM 主架构**。现有 V7 的三栏只是既有目标之一；如当前实际项目有所差异，应以能正常使用的布局为基线逐步优化，避免大规模重建。

- **顶栏**：浅暖白底、细下边框；左侧游戏标识和场景名，右侧时间/状态、帮助入口；避免所有指标争夺同等视觉权重。
- **导航区**：浅米色、树形缩进和当前 Area 高亮；未选节点低对比，选中项有柔和青绿底而非整块强对比色。
- **地图视口**：是画面主角。柔和绿灰远景，不加重型底纹；画布严格限制在原视口容器里。
- **词卡区**：暖白卡片、顶部物品图、下部英文/音标/中文含义、音频按钮；按 V7 显示规则区分模式。可视内容不应被地图画布压住。
- **底部操作提示**：弱化为一行提示，展示当前真正可执行的操作；重要错误提醒可以临时突出。

### 4.2 字体和尺寸

- 中文：优先系统无衬线或开源易读字体；英文：清晰的人文无衬线；音标需选支持 IPA 的字体回退链。
- 设计字号参考：主标题 20–24px，区域标题 14–17px，词汇英文 22–28px，拼写输入 20–24px，释义 15–17px，辅助文字 12–13px；实际以浏览器截图微调。
- 固定信息面板可采用 14–18px 圆角；地图底座与展示牌采用更小、统一的圆角体系。
- 页面保持稳定的 8px 间距系统（可使用 4px 半单位）；同级控件间距一致。

### 4.3 UI 状态视觉一致性

| 单词状态 | 节点形态 | 侧边辅助标志 |
|---|---|---|
| 未点亮 | 灰色细环、低亮度 | 空心圆 |
| 已点亮 | 柔金光环、轻微星点 | 星标 |
| 直接正确回忆 | 薄荷绿双环、短促确认动效 | 对勾 |
| 错误回忆 | 珊瑚红短脉冲、无永久强闪烁 | 叉号 |
| 错误后正确回忆 | 琥珀修复光环、缓和上升粒子 | 修复符号 |

**状态颜色与现有积分/状态机绑定，绝不通过视觉优化改变状态分值、历史覆盖规则或模式行为。** 颜色之外必须配合图标，降低色觉差异造成的误判。

### 4.4 动画时长与规范

- 普通 hover/按钮反馈 120–180ms；地图选中状态 180–260ms；节点点亮 350–500ms；场景过渡约 350–650ms。
- 动画使用 ease-out/自然缓动；避免多种光效同时叠加。
- 支持 `prefers-reduced-motion`：减少闪烁、缩放与位移，不影响结果提示。

## 5. 分层显示与画布边界——只修视觉问题，不换结构

- 始终维护一个**可见的主游戏视口**；使用已有渲染技术，不为换肤替换其引擎。若 Home/Scene 分属两个渲染器，同一时刻只有当前场景的一个参与可视呈现和输入。
- 画布的 CSS 宽高和像素宽高与容器同步；窗口改变时只调整尺寸与投影参数，不修改知识坐标或已保存的学习状态。
- 视觉层次由后到前：地图地面 → 道路和分区底板 → 单词底座和场景地标 → 人物与状态效果 → 仅属于地图视口的轻提示。常驻 HUD/导航/词卡在各自页面容器；全局对话框在独立顶层。
- 不让 `position: absolute` 的大面积信息板覆盖地图操作区，不让 Canvas 跨出父容器覆盖词卡，也不让图层顺序随场景进出发生变化。
- 以上属于**局部渲染和布局修复**；不得以此为由重建所有页面或改写地图数据。

统一词卡、输入框、状态环、进度条、场景过渡；提高色彩和动画一致性。验收：学习/练习规则与积分结果和改造前一致，练习模式不泄露词名。

**每个子补丁独立完成以下步骤：** 读取项目现状 → 列出受影响文件 → 写前后对比截图 → 最小修改 → 运行构建和回归测试 → 提交变更。失败则保留基线版本并修复该补丁，不开启下一补丁。

## 7. Git / GitHub 版本管理规则（执行前确保用户认可提交或推送）

### 7.1 为什么要采用

**Git 是本地版本控制系统；GitHub 是可选的远程代码托管与协作平台。** 即使暂时不连接 GitHub，也必须先建立 Git 历史。每次视觉调整都应在独立分支完成并保留明确的提交记录，以便对比与回退。GitHub 仓库建议设为 private，避免在公开仓库暴露尚未公开的素材和项目文件。

### 7.2 版本分类

- **规范版本**：`docs/specs/V5.md`、`docs/specs/V6.md`、`docs/specs/V7.md`，历史文件只追加存档、不原地改写。
- **增量补丁**：`docs/patches/V7.1-visual-design.md`（本文件）、后续 `V7.2-...md`、`V7.3-...md`；每个补丁需写影响范围、不改变什么、验证证据和回滚办法。
- **变更日志**：`CHANGELOG.md` 追加一条含版本、日期、行为变化、截图和相关提交号的记录。
- **开发协作规范**：项目根目录 `AGENTS.md`，约束 Codex 不能大规模覆盖现有设计、不能自行更改业务规则、应先跑测试再提交。
- **里程碑标签**：`v7.0-baseline`、`v7.1-visual`，对应当时的**代码版本**；文档版本号与代码版本标签不必一一对应，但要在日志中记录映射。

不要一次性把整个项目按本建议目录重构；仅在已有仓库上新建缺失的 `docs/` 文件，不移动现有源码与素材路径。

### 7.3 分支和提交约定

1. 在当前工作版本创建**基线 commit**；确认 `.gitignore` 已排除 `.env`、令牌、密钥、无关临时文件和个人隐私数据。
2. 新建 `feat/visual-v7.1` 分支，不直接在稳定 `main` 上执行视觉大改。
3. 按 A/B/C/D 分别提交，例如 `style: unify atelier palette`、`style: refine map surfaces`、`style: polish vocab cards`、`test: visual regression checks`。
4. 每个提交前至少检查 `git diff`、编译/构建、交互回归以及对应截图；不混入大量无关重构。
5. 如使用 GitHub，创建 Pull Request；在确认截图和功能正常后合并到 `main`。完成后可打稳定版本 Tag。未经授权，Codex 不自行 `push`、合并、删除分支、清空存档、执行破坏性 Git 命令。
6. 发现视觉方案效果不好时，用 Git 的受控回滚/恢复机制返回上一个稳定提交；不要靠手动粘贴旧版文件覆盖整个项目。
